## 背景

当前采集模块存在以下结构性缺陷：

1. **数据不全**：行业/地域字段经历 17 轮修补仍不稳定，K线数据缺失涨跌幅、昨收等字段
2. **数据源紧耦合**：每个数据源的 API 调用硬编码在 `AkShareAdapter` 的方法中，用 `if "em" in name` 判断走哪个分支
3. **降级逻辑分散**：`with_fallback` 装饰器、手写循环、多层 try-except 三种模式混用，行为不一致
4. **采集器重复代码**：三个 Collector 类各自实现了 DB 连接、日志、速率限制（约 30% 代码重复）
5. **能力不透明**：系统不知道"新浪不提供行业字段""腾讯不提供昨收"，采集后才发现数据缺失
6. **扩展困难**：新增数据源需要修改 `data_source.py`、`config.py`、`datasource_manager.py` 至少 3 个文件

## 目标

重构采集模块，实现：
- 数据源可插拔（新增数据源只需添加一个 Adapter 类）
- 自动感知数据缺失并从备用源补齐
- 采集器代码复用共享基类
- Web 界面可配置数据源

## 用户故事

- 作为一个运维人员，我希望在 Web 界面添加新的数据源（如券商私有接口），无需改代码
- 作为一个数据使用者，我希望采集的数据字段是完整的（行业、地域、涨跌幅、昨收等都有值）
- 作为一个开发者，我希望新增免费数据源时只需写一个新 Adapter 文件，放入 adapters 目录即可
- 作为一个系统管理员，我希望看到每个数据源的数据质量评分和字段覆盖率

## 功能需求

### 核心功能（必须做）

- [ ] **F1：DataProvider 抽象接口**
  - 定义统一的数据提供者接口，包含：provider_name、capabilities（声明能提供什么数据及哪些字段）、fetch 方法
  - 每个数据源实现此接口的一个或多个数据类别方法

- [ ] **F2：数据源注册中心（DataSourceRegistry）**
  - 自动发现/注册所有 DataProvider 实现
  - 按数据类别查询可用的 Provider 列表
  - 支持优先级排序（按 quality_score）

- [ ] **F3：数据编排器（DataOrchestrator）**
  - 核心调度：对每个数据类别，按质量优先级尝试各数据源
  - 字段补齐：主数据源字段缺失时，自动从备用数据源获取并合并
  - 统一降级：所有数据源失败时的兜底策略

- [ ] **F4：数据质量验证器（DataValidator）**
  - 采集完成后检查必填字段是否有值
  - 输出字段覆盖率报告
  - 标记哪些数据源提供了哪些字段

- [ ] **F5：BaseCollector 基类**
  - 提取三个 Collector 的公共逻辑：DB连接管理、建表、日志持久化、进度回调、速率限制
  - 三个采集器继承此基类

- [ ] **F6：重构现有数据源适配器**
  - 东方财富 → `adapters/akshare/eastmoney.py`
  - 新浪 → `adapters/akshare/sina.py`
  - 腾讯 → `adapters/akshare/tencent.py`
  - 必盈 → `adapters/biying.py`（从 `biying_adapter.py` 迁移）

- [ ] **F7：自定义 HTTP 数据源适配器**
  - `adapters/custom_http.py`：基于 Web 界面配置的 URL 模板生成数据源
  - 支持用户定义字段映射

- [ ] **F8：Web 界面数据源管理增强**
  - 显示每个数据源支持的数据类别和字段
  - 显示数据质量评分
  - 添加新数据源时可选"数据类别模板"
  - 优先级拖拽排序

### 扩展功能（有时间再做）

- [ ] **F9：数据源健康监控面板** — 显示各数据源近期成功率、响应延迟趋势图
- [ ] **F10：字段级别数据源配置** — 可以指定"行业字段只用必盈，K线用东方财富"
- [ ] **F11：WebSocket 数据源变更通知** — 数据源状态变更实时推送到前端

## 非功能需求

- 新增数据源：只需添加一个 Python 文件到 `adapters/` 目录，不超过 100 行代码
- 字段补齐：采集完成后，行业字段覆盖率 > 90%，地域字段覆盖率 > 80%
- 接口响应时间：数据源列表查询 < 200ms
- 向后兼容：现有的 `main.py` 命令行入口不受影响
- 不破坏现有数据库表结构

## 不做的事（范围边界）

- 不做实时数据流处理（本次只解决采集完整性）
- 不做数据源间数据一致性校验（如比较不同源的收盘价）
- 不做数据缓存层设计（现有 Caffeine 级别缓存不在本次范围）
- 不改变 OceanBase 数据库结构（可新增索引，不删改现有表）
